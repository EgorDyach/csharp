| `work_mem` | 4 MB |

| `seq_page_cost` / `random_page_cost` | 1 / 4 |
| `max_parallel_workers_per_gather` | 2 |
| Тестовая таблица | 1 000 000 строк, heap 85 MB, 10 827 страниц |
| Таблица сервиса | 1 000 003 заказа, 2 000 005 позиций |

**Методика.** Планы внутри каждой части получены в одном непрерывном прогоне, поэтому
цифры сопоставимы между собой. Перед ключевыми замерами выполняется прогревочный
прогон того же запроса: первый вызов читает страницы с диска и завышает `Execution Time`
в разы. Там, где важен объём ввода-вывода, используется `EXPLAIN (ANALYZE, BUFFERS)` —
счётчик `Buffers` объективнее времени, потому что не зависит от загрузки машины.

**Главное правило работы соблюдено:** ни один индекс не объявляется полезным без пары
измерений «до» и «после». В двух случаях измерение показало, что индекс **не нужен**, —
и он не был добавлен (задания 21 и 29).

# Часть 1. Тестовая база данных (задания 1–10)

## Задание 1–2. Таблица и данные

```sql
CREATE TABLE orders (
    id BIGSERIAL PRIMARY KEY,
    user_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    amount NUMERIC(10, 2) NOT NULL,
    created_at TIMESTAMP NOT NULL,
    updated_at TIMESTAMP NOT NULL
);

INSERT INTO orders (user_id, product_id, status, amount, created_at, updated_at)
SELECT
    (random() * 100000)::BIGINT,
    (random() * 10000)::BIGINT,
    (ARRAY['NEW','PAID','DELIVERED','CANCELLED'])[floor(random() * 4 + 1)::INT],
    random() * 10000,
    NOW() - (random() * INTERVAL '2 years'),
    NOW()
FROM generate_series(1, 1000000);

ANALYZE orders;
```

Результат: **1 000 000 строк, 85 MB, 10 827 страниц** (с учётом первичного ключа — 106 MB).

> **Ошибка в материалах задания.** Приведённый в методичке фрагмент
> `(ARRAY[...])[floor(random() * 4 + 1)]` не выполняется: `floor()` возвращает
> `double precision`, а индекс массива требует `integer`. Запрос падает с
> `array subscript must have type integer`. Исправлено приведением `::INT`.

## Задание 3. EXPLAIN

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 123;
```

```
 Gather  (cost=1000.00..17036.43 rows=11 width=53)
   Workers Planned: 2
   ->  Parallel Seq Scan on orders  (cost=0.00..16035.33 rows=5 width=53)
         Filter: (user_id = 123)
```

**1. Какой план выбрал PostgreSQL?** Параллельное последовательное сканирование: два
фоновых воркера и лидирующий процесс читают таблицу кусками, узел `Gather` собирает
результаты в один поток.

**2. Тип сканирования?** `Parallel Seq Scan` — полный проход по всем 10 827 страницам.
Индексов на этот момент нет, альтернативы у планировщика тоже.

**3. Как планируется найти строки?** Прочитать каждую и применить `Filter: (user_id = 123)`.
Оценка `rows=11` взята из статистики: планировщик знает число различных значений `user_id`
и делит на него общее число строк (1 000 000 / ≈100 000 ≈ 10).

Запись `cost=1000.00..17036.43` — две величины: стоимость до первой строки (у параллельного
плана ненулевая — нужно запустить воркеры) и до последней. Единица условная: 1.0 — чтение
одной страницы последовательным доступом.

## Задание 4. EXPLAIN ANALYZE

```
 Gather  (cost=1000.00..17036.43 rows=11 width=53) (actual time=0.164..10.334 rows=11 loops=1)
   Workers Planned: 2
   Workers Launched: 2
   Buffers: shared hit=10827
   ->  Parallel Seq Scan on orders  (cost=0.00..16035.33 rows=5 width=53) (actual time=... rows=4 loops=3)
         Filter: (user_id = 123)
         Rows Removed by Filter: 333330
         Buffers: shared hit=10827
 Planning Time: 0.025 ms
 Execution Time: 10.366 ms
```

| Показатель | Значение | Что означает |
|---|---|---|
| Тип сканирования | Parallel Seq Scan | полный проход |
| Planning Time | 0.025 ms | построение плана |
| Execution Time | 10.366 ms | реальное выполнение |
| actual rows | 11 | фактически вернулось |
| estimated rows | 11 | ожидание планировщика |
| Rows Removed by Filter | 333 330 × 3 | ≈1 000 000 прочитано и выброшено |
| Buffers | shared hit=10827 | 85 MB ради 11 строк |

**1. Чем EXPLAIN отличается от EXPLAIN ANALYZE?** Первый только строит план и показывает
оценки (`cost`, `rows`), запрос не выполняется. Второй действительно выполняет запрос и
добавляет факт: `actual time`, `actual rows`, `loops`. Практическое следствие: над
`INSERT`/`UPDATE`/`DELETE` он реально изменит данные — такие запросы оборачивают в
`BEGIN … ROLLBACK`.

**2. Почему EXPLAIN ANALYZE дольше?** Он делает работу, а не оценивает её. Плюс накладные
расходы на инструментирование: PostgreSQL снимает таймер на входе и выходе каждого узла
для каждой строки. На больших планах это искажает результат — тогда замеряют с
`EXPLAIN (ANALYZE, TIMING OFF)`.

**3. Estimated против actual?** `estimated` — предсказание по статистике из `pg_statistic`,
`actual` — факт. Здесь они совпали (11 и 11), потому что данные равномерны. Опасны
расхождения на порядки: они означают устаревшую статистику (лечится `ANALYZE`) или
неучтённую корреляцию колонок (лечится `CREATE STATISTICS`).

## Задание 5. Sequential Scan

```
5a. Seq Scan on orders  (cost=0.00..20827.00 rows=1000000)  Execution Time: 45.402 ms
5b. Seq Scan on orders  (cost=0.00..23327.00 rows=999900)   Execution Time: 61.862 ms
      Filter: (amount > '0'::numeric)
```

**1. Тип сканирования?** `Seq Scan` в обоих случаях, причём без распараллеливания:
результат нужен целиком, параллелизм не окупается.

**2. Почему Seq Scan?** В 5a условия нет — нужны все строки, индекс был бы лишним
посредником. В 5b условие есть, но под него подходят все 1 000 000 строк. Идти через
индекс — значит прочитать весь индекс, а потом всё равно всю таблицу.

Разница в `cost` (20 827 против 23 327) — цена самого фильтра: `cpu_operator_cost`,
умноженный на миллион строк.

**3. Всегда ли Seq Scan плох?** Нет. Последовательное чтение в разы быстрее случайного,
и на значительной доле таблицы выигрывает объективно. Проблема возникает, только когда
возвращается небольшая доля строк, а `Rows Removed by Filter` огромен — как в задании 4.

> **Вывод.** Seq Scan эффективнее индекса, когда выборка захватывает существенную часть
> таблицы (на этом стенде — примерно с 50 %), когда таблица помещается в несколько страниц,
> когда нужны все строки без фильтрации и когда результат требует полного прохода.

## Задание 6. Первый B-tree индекс

```sql
CREATE INDEX idx_orders_user_id ON orders(user_id);   -- 9080 kB
ANALYZE orders;
```

```
 Bitmap Heap Scan on orders  (cost=4.51..47.60 rows=11 width=53) (actual time=0.007..0.010 rows=11 loops=1)
   Recheck Cond: (user_id = 123)
   Heap Blocks: exact=11
   Buffers: shared hit=14
   ->  Bitmap Index Scan on idx_orders_user_id  (actual time=0.005..0.005 rows=11 loops=1)
         Index Cond: (user_id = 123)
         Buffers: shared hit=3
 Execution Time: 0.021 ms
```

| Метрика | До индекса | После индекса | Изменение |
|---|---|---|---|
| Тип Scan | Parallel Seq Scan | Bitmap Index Scan → Bitmap Heap Scan | — |
| Execution Time | 10.366 ms | **0.021 ms** | **быстрее в 494 раза** |
| Cost | 17 036.43 | 47.60 | в 358 раз меньше |
| Прочитано страниц | 10 827 | **14** | в 773 раза меньше |
| Обработано строк | 1 000 000 | 11 | — |
| Rows Removed by Filter | 333 330 × 3 | 0 | фильтр не нужен |
| Используемый индекс | нет | `idx_orders_user_id` | — |

**1. Изменился ли план?** Полностью: вместо чтения всей таблицы тремя процессами —
обращение к индексу и точечное чтение 11 страниц.

**2. Использует ли индекс?** Да. Условие переехало из `Filter` в `Index Cond` —
принципиальная разница: `Filter` применяется к уже прочитанным строкам, `Index Cond`
не даёт их прочитать.

**3. Насколько изменилось время?** С 10.4 мс до 0.021 мс. Честнее смотреть на `Buffers`:
10 827 страниц против 14 — эта величина не зависит от кэша и загрузки машины.

> **Наблюдение.** Планировщик выбрал не `Index Scan`, а Bitmap-пару — хотя строк всего 11.
> Причина: они лежат в 11 разных страницах (`Heap Blocks: exact=11`), то есть каждое
> обращение к таблице — случайное чтение. Bitmap-план собирает битовую карту нужных
> страниц, сортирует её по номеру страницы и читает таблицу по возрастанию адресов,
> превращая 11 случайных чтений в одно почти последовательное.

## Задание 7. Индекс есть, но используется не всегда

```sql
CREATE INDEX idx_orders_status ON orders(status);   -- 6848 kB
```

| Значение | Строк | Доля | План | Execution Time |
|---|---|---|---|---|
| PAID | 250 343 | 25.03 % | Bitmap Heap Scan | 21.427 ms |
| NEW | 250 475 | 25.05 % | Bitmap Heap Scan | 20.165 ms |
| DELIVERED | 249 024 | 24.90 % | Bitmap Heap Scan | 20.038 ms |
| CANCELLED | 250 158 | 25.02 % | Bitmap Heap Scan | 24.678 ms |

**1. Во всех ли случаях используется индекс?** На этих данных — да, во всех четырёх, и это
расходится с ожиданием задания. Причина в самих данных: генератор распределил статусы
строго поровну, «редкого» и «частого» статуса тут не существует. Чтобы найти настоящую
границу, поставлен отдельный эксперимент — задание 8.

Важно и то, почему при 25 % индекс всё ещё выигрывает: таблица целиком помещается в
`shared_buffers` (85 MB против 128 MB), случайное чтение фактически бесплатно, а индекс
по `status` компактный — 6.8 MB. На сервере с холодным кэшем и таблицей больше памяти
та же выборка ушла бы в `Seq Scan`.

**2. Почему может быть выбран Seq Scan?** Решение принимается по стоимости, а не по факту
существования индекса. Индексный доступ окупается, пока число обращений к таблице невелико.

**3. Как число строк влияет на план?** Решает не число строк, а число страниц. При
`user_id = 123` — `Heap Blocks: exact=11`, при `status = 'NEW'` — `exact=10827`, то есть
**все** страницы таблицы. Во втором случае индекс уже не экономит ввод-вывод.

## Задание 8. Селективность

Распределение: PAID 250 343 · CANCELLED 250 158 · NEW 250 475 · DELIVERED 249 024 (по ≈25 %).

| № | Условие | Строк | Доля | План | Cost | Время |
|---|---|---|---|---|---|---|
| 8.1 | `user_id = 123` | 11 | 0.001 % | Bitmap Index Scan | 47.60 | **0.062 ms** |
| 8.2 | `status = 'PAID'` | 250 343 | 25.0 % | Bitmap Heap Scan | 16 739 | 20.878 ms |
| 8.3 | то же, индекс запрещён | 250 343 | 25.0 % | Seq Scan | 23 327 | 44.755 ms |
| 8.4 | `status IN ('PAID','NEW')` | 500 818 | 50.1 % | Bitmap Heap Scan | 22 338 | 33.970 ms |
| 8.5 | `status <> 'PAID'` | 749 657 | 75.0 % | **Seq Scan** | 23 327 | 50.790 ms |

Строка 8.3 — контрольная: при 25 % выборки индексный план действительно быстрее полного
прохода (20.9 мс против 44.8 мс), то есть планировщик выбирает верно. Строки 8.4 и 8.5

четвертях планировщик от него отказывается.

> **Вывод.** Полезность индекса падает монотонно с ростом доли выбираемых строк: на

> раза, после ≈50 % — чистые накладные расходы. Причина одна: чем больше строк подходит,
> тем ближе число затронутых страниц к общему числу страниц таблицы.

## Задание 10. Bitmap Scan

```
 Bitmap Heap Scan on orders (status = 'NEW')   Heap Blocks: exact=10827   23.182 ms
 Bitmap Heap Scan on orders (user_id = 123)    Heap Blocks: exact=11       0.065 ms
 Seq Scan on orders (amount BETWEEN 1000 AND 3000, индекса нет)           55.744 ms
```

BitmapAnd — пересечение двух индексов:

```sql
EXPLAIN ANALYZE
SELECT * FROM orders
WHERE user_id BETWEEN 1000 AND 2000
  AND created_at > NOW() - INTERVAL '1 month';
```

```
 Bitmap Heap Scan on orders  (actual time=... rows=422 loops=1)
   Heap Blocks: exact=414
   ->  BitmapAnd
         ->  Bitmap Index Scan on idx_orders_user_id      (actual rows=9942)
         ->  Bitmap Index Scan on idx_orders_created_at   (actual rows=41414)
 Execution Time: 4.508 ms
```

Каждое условие по отдельности слабоселективно (9 942 и 41 414 строк), пересечение даёт 422
строки — и таблица читается в 414 страницах вместо 10 827.

**1. Что делает Bitmap Index Scan?** Проходит по индексу и вместо похода в таблицу за
каждой строкой строит в памяти битовую карту страниц (а если позволяет `work_mem` — и
строк внутри страниц). Наружу не отдаёт ни одной строки таблицы, поэтому `width=0`.

**2. Что делает Bitmap Heap Scan?** Получает карту, сортирует её по физическому порядку
страниц и читает таблицу по возрастанию адресов. `Recheck Cond` — обязательная
перепроверка: при нехватке `work_mem` карта вырождается из построчной в постраничную.

**3. Почему Bitmap вместо Index Scan?** Обычный `Index Scan` идёт в таблицу за каждой
строкой в порядке индекса — это случайные чтения, и одну страницу он может прочитать
многократно. Bitmap читает каждую страницу ровно один раз и последовательно. Правило:
`Index Scan` — единицы строк и запросы с `LIMIT`; `Bitmap Scan` — средние выборки;
`Seq Scan` — большие.

# Часть 2. Тестовая база данных (задания 11–21)

## Задание 11. Несколько условий и несколько индексов

```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 123 AND status = 'PAID';
```

```
 Bitmap Heap Scan on orders  (actual time=0.049..0.079 rows=2 loops=1)
   Recheck Cond: (user_id = 123)
   Filter: ((status)::text = 'PAID'::text)
   Rows Removed by Filter: 9
   ->  Bitmap Index Scan on idx_orders_user_id   (actual rows=11)
 Execution Time: 0.091 ms
```

**1. Один индекс или несколько?** Здесь — только один, `idx_orders_user_id`. Условие по
`status` осталось в `Filter`.

**2. Есть ли BitmapAnd?** В этом запросе нет. Пересекать карты имеет смысл, когда оба
условия дают крупные наборы, а их пересечение мало. Здесь первое же условие сужает выборку
до 11 строк — строить вторую карту дороже, чем проверить `status` у 11 прочитанных строк.

BitmapAnd появляется на другом запросе (см. задание 10): при условиях, дающих 9 942 и
41 414 строк, пересечение в 422 строки экономит чтение 10 400 страниц.

**3. Зачем объединять несколько индексов?** Чтобы сузить множество страниц до похода в
таблицу. Битовые карты — компактные структуры, их пересечение (`BitmapAnd`) или
объединение (`BitmapOr`) выполняется в памяти и стоит гораздо дешевле, чем лишние
случайные чтения.

## Задание 12. Составной индекс

```sql
CREATE INDEX idx_orders_user_status ON orders(user_id, status);   -- 20 MB
```

| Вариант | План | Rows Removed by Filter | Execution Time |
|---|---|---|---|
| Два отдельных индекса | Bitmap Heap Scan + Filter | 9 | 0.041 ms |
| Составной индекс | **Index Scan** | 0 | **0.010 ms** |

```
 Index Scan using idx_orders_user_status on orders  (actual time=0.005..0.005 rows=2 loops=1)
   Index Cond: ((user_id = 123) AND ((status)::text = 'PAID'::text))
```

**1. Какой вариант эффективнее?** Составной: вчетверо быстрее, и главное — оба условия
ушли в `Index Cond`, лишние строки вообще не читаются из таблицы.

**2. Всегда ли составной лучше?** Нет. Он занимает 20 MB против 6.8 MB у одноколоночного
`idx_orders_status`, замедляет запись и работает только для запросов, начинающихся с
`user_id`. Два отдельных индекса универсальнее: каждый обслуживает свой класс запросов и
может участвовать в `BitmapAnd`.

**3. От чего зависит выбор?** От того, встречаются ли условия вместе в реальных запросах.
Если пара `user_id + status` — устойчивый паттерн приложения, выгоден составной. Если
условия приходят порознь, дешевле держать одноколоночные и позволить планировщику
пересекать их битовыми картами.

## Задание 13. Порядок колонок

Созданы два индекса одинакового размера (по 30 MB): `(user_id, created_at)` и
`(created_at, user_id)`. Каждый проверен в изоляции — остальные индексы временно скрыты
внутри `BEGIN … ROLLBACK`.

| Запрос | `(user_id, created_at)` | `(created_at, user_id)` |
|---|---|---|
| `WHERE user_id = 123` | Bitmap Index Scan — **0.131 ms** | Parallel Seq Scan — 12.827 ms |
| `WHERE user_id = 123 AND created_at > …` | Index Scan — **0.025 ms** | Index Scan — 1.650 ms |
| `WHERE created_at > …` (без user_id) | Parallel Seq Scan — 45.734 ms | Bitmap Heap Scan — **10.964 ms** |

**1. Как порядок колонок влияет на применимость?** B-tree отсортирован по первой колонке,
внутри неё — по второй. Использовать индекс можно, только начиная с левого префикса. Поэтому
`(user_id, created_at)` бесполезен для запроса, где `user_id` не задан, — и наоборот.

**2. Почему это разные индексы?** Это два разных физических порядка строк. В первом все
записи одного пользователя лежат подряд и внутри отсортированы по дате; во втором подряд
лежат записи одного дня, а пользователи внутри перемешаны.

**3. Какой индекс кому подходит?** Запросу 1 — `(user_id, created_at)`. Запросу 3 —
`(created_at, user_id)`. Запросу 2 подходят оба, но `(user_id, created_at)` в 66 раз
быстрее: равенство по первой колонке сразу сужает диапазон, а во втором случае приходится
просматривать все записи месяца, проверяя `user_id`.

## Задание 14. WHERE + ORDER BY

На равномерных данных у каждого пользователя ~10 заказов — сортировать нечего, разницы
между планами не видно. Поэтому в таблицу добавлен крупный клиент (`user_id = 1`) с
**50 000 заказов**: это реальный сценарий, ради которого индекс под сортировку и нужен.

```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 1 ORDER BY created_at DESC;
```

| Вариант | План | Execution Time |
|---|---|---|
| Без составного индекса | Bitmap Heap Scan → **Sort** (external merge, 3432 kB на диск) | 13.563 ms |
| С `(user_id, created_at DESC)` | Bitmap Heap Scan → **Sort** (тот же план!) | 17.012 ms |
| Форсированный Index Scan | Index Scan, без Sort, но **49 920 буферов** | 25.013 ms |
| С индексом + `LIMIT 100` | **Index Scan, без Sort, 102 буфера** | **0.092 ms** |

**1. Исчезла ли операция Sort?** Без `LIMIT` — нет, и планировщик здесь прав. Проверка
гипотезы (третья строка таблицы) показывает почему: `Index Scan` по 50 000 строк делает
50 000 отдельных обращений к таблице — 49 920 буферов против 600 у Bitmap-плана. Дешевле
прочитать страницы пачкой и отсортировать результат, даже с выгрузкой во временный файл.

Как только появляется `LIMIT 100`, картина переворачивается: индекс отдаёт строки уже
в нужном порядке, и достаточно прочитать первые сто. Sort исчезает, время падает
со 17 мс до 0.092 мс — **в 185 раз**.

**2. Почему индекс может использоваться для сортировки?** B-tree физически хранит ключи
упорядоченными, поэтому обход индекса — это уже отсортированная последовательность.
PostgreSQL умеет читать его в обе стороны (`Index Scan Backward`), так что одноколоночный
индекс закрывает и `ASC`, и `DESC`.

**3. Почему важен порядок колонок?** Индекс даёт готовый порядок только для того набора
колонок и направлений, в котором построен. `(user_id, created_at DESC)` обслуживает
«фильтр по пользователю + сортировка по дате убыв.»; для `ORDER BY status, created_at`
он бесполезен. Явный `DESC` в определении нужен, когда направления в `ORDER BY` смешаны
(`a ASC, b DESC`) — для одной колонки хватает и обратного обхода.

## Задание 16. Index Only Scan

| Запрос | План | Heap Fetches | Время |
|---|---|---|---|
| `SELECT id, user_id` (индекса нет) | Bitmap Heap Scan | — | 3.978 ms |
| `SELECT id, user_id` + `(user_id, id)` | **Index Only Scan** | **0** | **4.402 ms** |
| `SELECT id, user_id, amount` | Bitmap Heap Scan | — | 4.324 ms |
| `SELECT id, status, created_at` + `INCLUDE` | **Index Only Scan** | **0** | 5.158 ms |

**1. Чем Index Only Scan отличается от Index Scan?** Обычный `Index Scan` использует индекс
как указатель и всё равно идёт в таблицу за остальными колонками. `Index Only Scan` берёт
все нужные данные прямо из индекса и к таблице не обращается — в плане это видно по строке
`Heap Fetches: 0`.

**2. Почему PostgreSQL может не обращаться к таблице?** Из-за карты видимости (visibility
map). Индекс не хранит информацию о том, видима ли версия строки текущей транзакции, —
эта информация лежит в таблице. Но если страница целиком помечена в карте видимости как
«все версии видны всем», проверять нечего. Карту обновляет `VACUUM`, поэтому после
массовых изменений `Heap Fetches` растёт, пока не отработает автовакуум.

**3. Какие условия нужны?** Все колонки из `SELECT`, `WHERE`, `ORDER BY` и `GROUP BY`
должны входить в индекс (третья строка таблицы: добавили `amount` — и план сразу вернулся
к обычному Bitmap). Плюс актуальная карта видимости.

**Дополнительное задание — INCLUDE.** `INCLUDE (id, status, created_at)` кладёт колонки в
листья индекса как полезную нагрузку, не делая их частью ключа: дерево остаётся
отсортированным только по `user_id`, а Index Only Scan становится возможен. Плата —
размер: 54 MB против 32 MB у `(user_id, id)`.

## Задание 17. Partial Index

**Сценарий из задания** (`status = 'NEW'`, 25 % таблицы): partial index занимает 5792 kB
против 21 MB у полного, время `LIMIT 100` падает с 0.621 мс до 0.137 мс — выигрыш есть,
но скромный.

**Сценарий, ради которого partial index и придуман.** Задание предполагает, что `NEW`
встречается редко, но генератор раздал статусы поровну. Поэтому создан действительно
редкий статус — `REFUND_PENDING`, 0.5 % строк:

| Метрика | Обычный индекс по `status` | Partial index | Изменение |
|---|---|---|---|
| Размер | 7 232 kB | **136 kB** | в 53 раза меньше |
| План | Index Scan по `created_at` + Filter | Index Scan по partial | — |
| Rows Removed by Filter | 21 048 | **0** | — |
| Execution Time | 36.626 ms | **0.080 ms** | **в 458 раз быстрее** |

**2. Когда полезен?** Когда приложение регулярно спрашивает небольшое подмножество: очередь

**3. Почему один partial index не покрывает все запросы?** Планировщик применяет его,
только если может доказать, что условие запроса влечёт условие индекса. Запрос по
`status = 'PAID'` этот индекс использовать не может (проверено: 0.404 мс через обычный

разумно ровно до тех пор, пока подмножеств немного.

## Задание 18. Expression Index

```sql
CREATE TABLE users (id BIGSERIAL PRIMARY KEY, email VARCHAR(255) NOT NULL);
-- 500 001 строка
CREATE INDEX idx_users_email ON users(email);

EXPLAIN ANALYZE SELECT * FROM users WHERE LOWER(email) = 'test@example.com';
```

| Запрос | План | Время |
|---|---|---|
| `WHERE LOWER(email) = …`, есть индекс по `email` | Parallel Seq Scan | 22.962 ms |
| `WHERE email = 'Test@Example.COM'` (без функции) | Index Scan | 0.025 ms |
| `WHERE LOWER(email) = …` + индекс по `LOWER(email)` | **Index Scan** | **0.024 ms** |

**Почему обычный индекс по `email` не используется?** Индекс хранит значения колонки как
есть — `'User1@Example.com'`. Запрос же спрашивает про значение **функции** от колонки.
PostgreSQL не знает, как из отсортированного набора исходных строк получить порядок их
`LOWER()`-версий, и не имеет права предполагать, что функция сохраняет порядок. Поэтому
единственный способ — вычислить `LOWER()` для каждой строки, а это полный проход.

> **Вывод.** Индекс применим, только если выражение в `WHERE` совпадает с тем, по которому
> индекс построен. Любая обёртка над колонкой — `LOWER()`, `DATE()`, `CAST`, арифметика —
> делает обычный индекс неприменимым. Решений два: либо строить индекс по тому же выражению
> (`CREATE INDEX ... ON users(LOWER(email))`, 19 MB), либо переписать запрос так, чтобы
> колонка осталась «голой» (например, хранить email уже нормализованным).

## Задание 19. Цена индексов при записи

Замер на двух одинаковых таблицах: одна без индексов, вторая с пятью.

| Операция | Без индексов | С 5 индексами | Замедление |
|---|---|---|---|
| `INSERT` 200 000 строк | 205.929 ms | **1450.335 ms** | **в 7.0 раза** |
| `UPDATE` 50 000 строк | 58.059 ms | **631.598 ms** | **в 10.9 раза** |
| Размер данных | 21 MB | 21 MB | — |
| Размер индексов | 0 bytes | **31 MB** | индексы больше данных |

**1. Как изменилось время INSERT?** Выросло в семь раз, `UPDATE` — почти в одиннадцать.

**2. Почему?** Вставка одной строки в таблицу — это дозапись в конец страницы. Но каждый
индекс требует найти нужное место в B-дереве и вставить туда запись, при переполнении
страницы — расщепить её. Пять индексов означают пять таких операций плюс пять записей в
WAL. `UPDATE` страдает сильнее: из-за MVCC создаётся новая версия строки, и на неё нужно
завести записи во всех индексах, даже если изменённая колонка в них не входит (оптимизация
HOT работает, только когда новая версия помещается в ту же страницу и колонка не
проиндексирована).

**3. Что происходит с индексами при добавлении строки?** В каждый индекс добавляется пара
«ключ → TID новой версии». Старые записи не удаляются сразу — они остаются, пока `VACUUM`
не убедится, что старая версия строки больше никому не видна.

**3. Можно ли считать индекс с `idx_scan = 0` бесполезным?** Нет, и `orders_pkey` — прямое
тому подтверждение. Причины:
- уникальные индексы обеспечивают **ограничение целостности**, а не только поиск: удалив
  `orders_pkey`, мы разрешим дубликаты;
- на первичный ключ могут ссылаться внешние ключи других таблиц;
- статистика накапливается с момента последнего `pg_stat_reset()` — короткое окно
  наблюдения ничего не доказывает;
- индекс может обслуживать редкий, но критичный сценарий: ночной отчёт, админскую

- реплики ведут свою статистику: на мастере ноль, на реплике сотни обращений.

**4. Риски при удалении.** Уронить целостность (уникальность, внешние ключи), сломать
редкий тяжёлый запрос, спровоцировать деградацию под нагрузкой. Обратное создание индекса
на большой таблице — долгая операция, а обычный `CREATE INDEX` берёт блокировку на запись
(нужен `CONCURRENTLY`). Безопасный порядок: убедиться, что индекс не уникальный и не
обслуживает FK → проверить статистику на всех репликах за длительный период →
сначала пометить невидимым для планировщика или удалить в непиковое время с готовым
скриптом отката.

## Задание 21. Финальная оптимизация

```sql
SELECT id, amount, status, created_at
FROM orders
WHERE user_id = $1 AND status = 'PAID' AND created_at >= NOW() - INTERVAL '30 days'
ORDER BY created_at DESC
LIMIT 50;
```

| Вариант | План | Rows Removed | Время |
|---|---|---|---|
| Только одноколоночные индексы | Index Scan Backward по `created_at` + Filter | 3 791 | 118.857 ms |
| `(user_id, created_at DESC)` | Index Scan + Filter по `status` | 148 | 0.310 ms |
| **`(user_id, status, created_at DESC)`** | **Index Scan, всё в Index Cond** | **0** | **0.080 ms** |

Итог: **118.857 мс → 0.080 мс, ускорение в 1486 раз.**

**Проблема исходного плана.** Планировщик заходил с самой «широкой» стороны — шёл по
индексу дат от свежих к старым и проверял `user_id` и `status` у каждой строки, отбросив
3 791 запись, прежде чем набрать нужные 50.

**Объяснение порядка колонок.** Сначала идут условия равенства — `user_id`, затем `status`;
они сужают дерево до узкого поддиапазона. Последней стоит колонка диапазонного условия и
сортировки — `created_at DESC`: внутри выбранной пары значений записи уже упорядочены по
дате, поэтому `LIMIT 50` останавливает чтение сразу. Правило общее: **сначала равенства,
потом диапазон и сортировка**.

**Проверка гипотезы: нужен ли covering-индекс?** Дополнительно проверен вариант
`INCLUDE (amount)` — теоретически он позволил бы Index Only Scan. Измерение показало
обратное: планировщик его игнорирует (0.072 мс против 0.080 мс — разница в пределах шума),
потому что при `LIMIT 50` обычный Index Scan и так читает всего 57 страниц, а индекс
дороже: 54 MB против 45 MB. **Индекс удалён** — платить за него при записи незачем.

## Задание 22. Scaling Entity

**Сущность: `orders`** (таблица заказов ChakChakShop).

**За что отвечает.** Заказ клиента: кто, на какую сумму, в каком статусе, когда создан.

**Почему растёт быстрее остальных.** Каталог чак-чака конечен — 7 продуктов и 3 категории,

`order_items` растёт ещё быстрее (2–3 позиции на заказ), но это производная сущность:
она читается всегда по `order_id`, то есть точечно.

**Ожидаемый объём через год.** При 500 заказах в сутки — ~180 тыс. в год; при выходе на
5 000 заказов в сутки — ~1.8 млн в год плюс 4–5 млн позиций. Именно поэтому для замеров
таблица заполнена **1 000 000 заказов и 2 000 005 позиций**: это реалистичный горизонт
одного-двух лет работы.

**Поля для поиска и фильтрации.** `user_id` (личный кабинет), `created_at` (сортировка

## Задание 26. Потенциальные проблемы

| Запрос | Проблема | Seq Scan | Селективность | Подходящий индекс | Можно ли изменить SQL |
|---|---|---|---|---|---|
| Query 1 | Sort с выгрузкой на диск; возвращает **все** 50 003 заказа клиента | нет | 5 % | нет | да — нужен `LIMIT` |
| Query 2 | нет | нет | 1 строка | есть | нет |
| Query 3 | **читает всю таблицу** и сортирует 30 MB во временных файлах | **да** | 100 % | нет | да — `LIMIT`/`OFFSET` |
| Query 4 | лишние 39 755 строк отброшены фильтром | нет | 2 % | частично | да |

**Главная находка — не индекс, а код.** `OrderService.GetOrdersAsync` устроен так:

```csharp
var orders = await _orderRepository.GetAllAsync(cancellationToken);
var totalCount = orders.Count();
var pagedOrders = orders.Skip(request.Skip).Take(request.PageSize).ToList();
```

Пагинация выполняется **в памяти приложения**: база отдаёт миллион строк, C# оставляет из
них десять. Никакой индекс это не лечит — пока в SQL нет `LIMIT`, PostgreSQL обязан вернуть
всё. То же и в `GetUserOrdersAsync`: endpoint `/api/orders/my` отдаёт клиенту все его
50 003 заказа одним ответом.

приблизительный счётчик из `pg_class.reltuples`, кэш в Redis (он уже есть в проекте) или
отказ от общего числа страниц в пользу курсора.

зафиксировано комментарием прямо в файле миграции.

# Задание 30. Почему нельзя индексировать всё

Ответ опирается на измерения из заданий 19 и 29.

**Размер и стоимость хранения.** В тестовой таблице `orders` данные занимают 89 MB, а
тринадцать индексов — **266 MB**, втрое больше самих данных. В базе сервиса после миграции:
85 MB данных против 104 MB индексов. Индексы конкурируют с данными за `shared_buffers`:
чем больше служебных структур, тем меньше страниц самой таблицы помещается в кэш — и
запросы, которым индексы не помогают, начинают читать с диска.

**INSERT.** Замер задания 19: вставка 200 000 строк заняла 205.9 мс без индексов и
1450.3 мс с пятью — **в 7 раз дольше**. Каждый индекс требует найти позицию в B-дереве,
вставить запись, при переполнении расщепить страницу и записать всё это в WAL.

**UPDATE.** 58.1 мс против 631.6 мс — **в 10.9 раза дольше**. Из-за MVCC обновление создаёт
новую версию строки, и на неё нужно завести записи во всех индексах. Оптимизация HOT
(update без обновления индексов) работает только когда новая версия помещается в ту же
страницу и изменённая колонка не проиндексирована — то есть чем больше индексов, тем реже
она применима.

**DELETE.** Удаление не убирает записи из индексов сразу: строка лишь помечается мёртвой,
а чистить индексы будет `VACUUM`. Чем больше индексов, тем дольше вакуум и тем больше
раздувание (bloat) между его проходами.

**Влияние на скорость записи в целом.** Запись — это точка, где расходы складываются:
каждая вставка платит за все индексы сразу, независимо от того, используется ли конкретный
индекс хоть кем-нибудь.

**Реальное использование запросами.** Статистика задания 20 показывает, что из тринадцати
индексов реально работали три (`idx_scan` 14–17), а половина сработала один-два раза.
Индекс, созданный «на всякий случай», не ускоряет ничего, но исправно берёт плату при
каждой записи. Показателен и задание 21: covering-индекс на 54 MB планировщик просто
проигнорировал — он оказался дороже обычного.

**Наконец, лишние индексы вредят самому планировщику.** Чем больше альтернатив, тем больше
комбинаций он перебирает; на сложных запросах растёт `Planning Time`, а при неудачной
статистике повышается риск выбрать неверный план.

> **Итог.** Индекс — это не бесплатное ускорение, а сделка: выигрыш на чтении конкретного
> класса запросов в обмен на постоянные расходы при записи и на диске. Заключать её стоит
> только тогда, когда выигрыш подтверждён измерением на реальном запросе — и отказываться,
> когда измерение показало обратное, как в заданиях 21 и 29.
