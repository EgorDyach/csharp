# Лабораторная работа №5. Шардирование PostgreSQL: Router и Consistent Hashing

Пять миллионов заказов сервиса ChakChakShop разложены по трём независимым
экземплярам PostgreSQL, роутер живёт в коде сервиса. Две стратегии
распределения сравниваются не по описанию, а по количеству реально
перевезённых строк. Сырые логи прогонов — в [`raw/`](raw).

**Отчёт для защиты:** https://claude.ai/artifact/KENqVSQWM3BMFuo9ADYNZo

---

## 1. Выбор данных для шардирования

**Сущность — `orders`.** В базе сервиса это единственная таблица, которая
растёт неограниченно: 5 000 005 строк против 50 004 в `users`, 7 в
`products` и 4 в `categories`. Остальное шардировать нечего.

**Shard key — `user_id`.** Не `id` самого заказа, хотя он тоже уникален
и хорошо хешируется.

Причина в том, какие запросы у сервиса главные. Ключ шардирования
обязан присутствовать в условии как можно большего числа запросов —
иначе роутер не знает, к какому узлу идти, и приходится опрашивать все.
У ChakChakShop запросы такие:

| Запрос API | Условие | Есть ли `user_id` |
|---|---|---|
| `GET /api/orders/my` | `WHERE user_id = ?` | **да** |
| `POST /api/orders` | вставка заказа клиента | **да** |
| `GET /api/orders/{id}` | `WHERE id = ?` | нет |
| `GET /api/orders?from=&to=` | `WHERE created_at BETWEEN` | нет |

Выбор `user_id` даёт ещё одно важное свойство: **все заказы клиента
лежат на одном узле**. Это делает локальными не только выборку, но и
`JOIN` заказа с его позициями, и пересчёт суммы по клиенту. Если
шардировать по `id` заказа, заказы одного человека размазались бы по
всем узлам и даже простой список «мои заказы» стал бы распределённым.

Почему **не** `created_at`: диапазонное шардирование по дате означает,
что вся запись идёт в один «текущий» шард, а остальные простаивают.
Почему **не** `status`: три-четыре значения — это кардинальность, при
которой больше трёх шардов просто не сделать.

**Насколько равномерно он распределяет данные** — вопрос, у которого,
как выяснилось, два разных ответа. Он разобран в задании 4.

## 2. Четыре экземпляра PostgreSQL

Полный фрагмент — [`infra/docker-compose.shards.yml`](infra/docker-compose.shards.yml).

| | Контейнер | Порт снаружи | В сети compose |
|---|---|---|---|
| Shard 0 | `chakchakshop_shard0` | 5501 | `shard0:5432` |
| Shard 1 | `chakchakshop_shard1` | 5502 | `shard1:5432` |
| Shard 2 | `chakchakshop_shard2` | 5503 | `shard2:5432` |
| Shard 3 | `chakchakshop_shard3` | 5504 | `shard3:5432` |

Принципиальный момент: **это не кластер**. Между этими базами нет ни
репликации, ни общего каталога, ни распределённых транзакций. Каждая
из них — обычный одиночный PostgreSQL, который ничего не знает
о существовании соседей. Связывает их только код роутера в сервисе.

Шард 3 поднят сразу, но до задания 5 остаётся пустым — он нужен, чтобы
вживую показать расширение кластера.

Схема на каждом узле — [`sql/02-shard-schema.sql`](sql/02-shard-schema.sql):

```sql
CREATE TABLE orders (
    id uuid PRIMARY KEY, user_id uuid NOT NULL, ...
);

CREATE TABLE order_items (
    id uuid PRIMARY KEY, order_id uuid NOT NULL,
    user_id uuid NOT NULL,   -- денормализация ради co-location
    ...
);
```

Две детали, которых не было в исходной схеме и которые продиктованы
именно шардированием:

1. **`user_id` добавлен в `order_items`.** Без него позицию заказа
   некуда маршрутизировать: роутер умеет считать шард только от ключа.
   Денормализация здесь не оптимизация, а необходимость.
2. **`users`, `products`, `categories` копируются на каждый шард целиком.**
   Они маленькие и нужны всем узлам. Это стандартный приём — reference
   tables реплицируются, чтобы `JOIN` к ним оставался локальным.

## 3. Router

### Хеш-функция

Роутер живёт в C#, а раскладка пяти миллионов строк считалась в SQL.
Обе стороны обязаны давать **один и тот же** номер шарда, иначе запрос
уйдёт на узел, где данных нет, — и вернёт не ошибку, а пустой ответ.
Такое в проде почти невозможно заметить.

Поэтому хеш выбран так, чтобы его можно было воспроизвести буква в букву
в любом языке: первые 15 шестнадцатеричных цифр MD5, то есть 60 бит.
Пятнадцать, а не шестнадцать — чтобы значение гарантированно оставалось
положительным в знаковом 64-битном целом и остаток не оказался
отрицательным.

```csharp
public static long Compute(string key)
{
    var digest = MD5.HashData(Encoding.UTF8.GetBytes(key));
    var hex = Convert.ToHexString(digest).ToLowerInvariant();
    return long.Parse(hex.AsSpan(0, 15), NumberStyles.HexNumber, CultureInfo.InvariantCulture);
}
```

```sql
CREATE FUNCTION shardlab.shard_hash(p_key text) RETURNS bigint AS $$
    SELECT ('x0' || substr(md5(p_key), 1, 15))::bit(64)::bigint;
$$ LANGUAGE sql IMMUTABLE;
```

Чего здесь сознательно **нет**: `string.GetHashCode()` — начиная
с .NET Core он рандомизирован и меняется от запуска к запуску процесса;
`hashtext()` в PostgreSQL — внутренняя функция без гарантий совместимости
между версиями. MD5 взят не ради криптографии, а ради равномерности:
ключ шардирования не защищают, его распределяют.

### Стратегия 1: hash(key) % N

```csharp
public int ResolveShard(string shardKey) => (int)(ShardHash.Compute(shardKey) % ShardCount);
```

### Стратегия 2: Consistent Hashing

```csharp
// Имя виртуального узла собирается ровно так же, как в SQL: 'shard-<id>#<n>'
for (var shard = 0; shard < shardCount; shard++)
    for (var vnode = 0; vnode < virtualNodes; vnode++)
        ring.Add((ShardHash.Compute($"shard-{shard}#{vnode}"), shard));

ring.Sort((a, b) => a.Position.CompareTo(b.Position));
```

```csharp
public int ResolveShard(string shardKey)
{
    var hash = ShardHash.Compute(shardKey);

    // Первая точка кольца справа от ключа. BinarySearch на промахе
    // возвращает дополнение индекса вставки — это и есть нужная точка.
    var index = Array.BinarySearch(_positions, hash);
    if (index < 0) index = ~index;
    if (index >= _positions.Length) index = 0;   // кольцо замкнулось

    return _owners[index];
}
```

Виртуальные узлы обязательны. Три точки, разбросанные хеш-функцией по
кольцу, лягут как попало, и один шард заберёт половину диапазона.
256 точек на шард сглаживают это до единиц процентов — но не до нуля,
что видно ниже.

Доля кольца на каждый шард при 256 vnode (`GET /api/sharding/ring`):

```json
{ "0": 31.05, "1": 33.88, "2": 35.06 }
```

Это не формальность, а защита от самой неприятной ошибки в шардировании.
[`infra/04-hash-parity.py`](infra/04-hash-parity.py) берёт 60 случайных
ключей и сверяет три величины: сам хеш, номер шарда по модулю и номер
шарда по кольцу.

```

  195ffa31-9ec7-4a10-9b15-42e4136b1001  hash=65779107496383  modulo=0  ring=0  ✓
```

## 4. Распределение данных

Перенос идёт потоком: исходная база отдаёт `COPY ... TO STDOUT`, шард
принимает `COPY ... FROM STDIN` ([`infra/03-load-shards.sh`](infra/03-load-shards.sh)).
Между узлами нет ни FDW, ни репликации — ровно так же выглядят настоящие
миграции данных между независимыми серверами.

```
Shard 0 ->    2467541 записей, 654 MB
Shard 1 ->    2214344 записей, 583 MB
Shard 2 ->     318120 записей, 200 MB
```

### Насколько равномерно распределились данные

Здесь обнаружилось самое интересное в этой работе. У вопроса
«равномерно ли?» оказалось **два разных ответа**, и они противоположны.

**По ключам распределение практически идеальное:**

| Шард | Пользователей | Доля |
|---|---|---|
| 0 | 16 700 | 33.397 % |
| 1 | 16 550 | 33.097 % |
| 2 | 16 754 | 33.505 % |

**По объёму данных — катастрофическое:**

| Шард | Заказов | Доля |
|---|---|---|
| 0 | 2 467 541 | **49.351 %** |
| 1 | 2 214 344 | 44.287 % |
| 2 | 318 120 | **6.362 %** |

Разброс между самым большим и самым маленьким шардом — 129 % от среднего.

### Почему так вышло

```sql
SELECT u.username, a.orders_count FROM shardlab.user_assignment a
JOIN users u ON u.id = a.user_id ORDER BY a.orders_count DESC LIMIT 4;
```

```
      username       | orders_count
---------------------+--------------
 loadtest_user_46594 |      1900268
 loadtest_user_14353 |      1900019
 customer            |       249760
 loadtest_user_12989 |           39
```

```
 avg_orders | median_orders | p99_orders | max_orders
------------+---------------+------------+------------
      99.99 |            19 |         30 |    1900268
```

Медиана — 19 заказов на клиента, 99-й перцентиль — 30, а два аккаунта
держат по 1.9 миллиона каждый. Это следы нагрузочного генератора из
лабораторной работы №2, оставшиеся в наборе данных. Разбираться с ними
я не стал намеренно: они дали работе честный и очень наглядный
hot-key-сценарий, который иначе пришлось бы выдумывать.

Что данные на этих двух аккаунтах синтетические — видно сразу.
Что **ситуация** реальна — тоже: ровно так выглядит любой SaaS, где один
корпоративный клиент генерирует больше трафика, чем все остальные вместе.

### Проверка: виновата ли хеш-функция

Нет. Если убрать два аномальных аккаунта, распределение по объёму
становится таким же ровным, как по ключам:

| Шард | Заказов без аномалий | Доля |
|---|---|---|
| 0 | 317 513 | 33.42 % |
| 1 | 314 325 | 33.09 % |
| 2 | 318 120 | 33.49 % |

**Вывод: хеш распределяет ключи, а не объём.** Объём он распределяет
ровно настолько, насколько равномерно объём размазан по ключам. Никакая
функция не поможет, если один ключ весит больше, чем треть базы.

### Может ли такой дисбаланс стать проблемой

Уже стал. Shard 0 — 654 MB, Shard 2 — 200 MB, втрое меньше. При такой
раскладке первый узел упрётся в диск и память втрое раньше третьего,
резервное копирование будет идти втрое дольше, а любой перенос данных
затронет в основном его. Подробный разбор последствий для запросов —
в лабораторной работе №6.

## 5. Что произойдёт при добавлении нового shard

Задание: посчитать, сколько записей сменят шард при переходе с
`hash(key) % 3` на `hash(key) % 4`.

```sql
SELECT count(*) FILTER (WHERE mod_3 <> mod_4)                   AS users_moved,
       sum(orders_count) FILTER (WHERE mod_3 <> mod_4)          AS orders_moved,
       round(100.0 * sum(orders_count) FILTER (WHERE mod_3 <> mod_4)
             / sum(orders_count), 2)                            AS orders_moved_pct
FROM shardlab.user_assignment;
```

```
 users_moved | users_stayed | orders_moved | orders_stayed | orders_moved_pct
-------------+--------------+--------------+---------------+------------------
       37475 |        12529 |      4761282 |        238723 |            95.23
```

**Переезжают 37 475 клиентов из 50 004 — 74.94 % ключей.** Это ровно то
число, которое предсказывает теория: остаток от деления на 4 совпадает
с остатком от деления на 3 примерно у каждого четвёртого ключа, значит
остальные три четверти меняют адрес.

По объёму получилось ещё хуже — 95.23 %, потому что оба аккаунта-гиганта
попали в число переезжающих.

Куда именно едут данные:

```
 from_shard | to_shard | orders
------------+----------+---------
          0 |        0 |   79947     <- остались
          0 |        1 |   79131
          0 |        2 |   80117
          0 |        3 | 2228346
          1 |        0 |   79118
          1 |        1 |   78990     <- остались
          1 |        2 | 1977262
          ...
```

### Почему добавление одного узла двигает почти всё

Потому что `% N` — это не адрес, а **функция от размера кластера**.
Ключ не «принадлежит» шарду 2; он принадлежит остатку от деления на три.
Меняется делитель — меняется вся система адресов сразу для всех ключей.

Обратите внимание на строку `1 -> 2` с почти двумя миллионами заказов:
это данные, которые переезжают **между двумя старыми узлами**. Новый шард
тут вообще ни при чём. Кластер перетасовывает сам себя.

## 6–7. Consistent Hashing и сравнение стратегий

Тот же переход 3 → 4, но по кольцу:

```
 users_moved | users_stayed | orders_moved | orders_stayed | orders_moved_pct
-------------+--------------+--------------+---------------+------------------
       12813 |        37191 |      2393593 |       2606412 |            47.87
```

### Итоговое сравнение

| | Перемещено ключей | Перемещено объёма | Объём без аномальных аккаунтов |
|---|---|---|---|
| `hash(key) % N` | **74.94 %** | 95.23 % | 74.87 % |
| Consistent Hashing | **25.62 %** | 47.87 % | 25.67 % |

Колонка без аномалий показывает чистое поведение алгоритмов: 74.87 %
против 25.67 %, то есть ровно `1 - 1/N` против `1/N`. Теория сошлась
с практикой до десятых долей процента.

### Физический переезд, а не только проценты

[`infra/05-add-fourth-shard.sh`](infra/05-add-fourth-shard.sh) реально
перевозит данные на shard3 по каждой из стратегий:

```
hash(key) % 4          перевезено    2385203 заказов,   485 MB, время   31.0 с
consistent hashing     перевезено    2393593 заказов,   487 MB, время   27.0 с
```

На первый взгляд — никакой разницы. И вот здесь прячется главное:

```
      strategy      | reshuffled_between_old_nodes | moved_to_new_node | total_moved
--------------------+------------------------------+-------------------+-------------
 hash % N           |                      2376079 |           2385203 |     4761282
 Consistent Hashing |                         NULL |           2393593 |     2393593
```

**На новый узел в обоих случаях уезжает примерно одинаково — около
2.4 млн заказов. Разница в том, что при `hash % N` ещё 2 376 079 записей
тасуются между старыми узлами, а при consistent hashing между ними не
переезжает ничего. Ноль.**

Это и есть ответ на вопрос «почему результаты отличаются».

### Почему Consistent Hashing уменьшает объём переноса

Потому что он меняет природу адреса. В `% N` адрес вычисляется от
размера кластера, и размер входит в формулу для каждого ключа. На кольце
адрес ключа — это его собственная позиция, которая не зависит ни от
количества узлов, ни от их состава. Меняется не адрес ключа, а только то,
какой узел за этот участок кольца отвечает.

Новый узел встаёт на кольцо своими точками и отрезает себе куски
у соседей справа. Всё, что лежит вне этих кусков, даже не узнаёт
о случившемся.

### Что произойдёт, если добавить ещё один shard

То же самое, но меньше: при переходе 4 → 5 переедет около 1/5 ключей,
при 5 → 6 — около 1/6. Доля переносимых данных — это всегда примерно
`1/N` от общего объёма, и она падает по мере роста кластера. У `% N`
она, наоборот, всегда остаётся около `1 - 1/N`, то есть растёт.

### Что произойдёт, если удалить shard

Симметрично. Данные удалённого узла «пролетают» мимо его точек по
часовой стрелке и достаются следующим узлам, а всё остальное остаётся
на месте — переедет около `1/N` данных, и только те, что лежали на
удалённом узле. У `% N` удаление узла так же катастрофично, как
и добавление: делитель меняется, адреса пересчитываются у всех.

## 8. Итог

**Shard** — самостоятельный экземпляр базы, хранящий свою часть данных.
Не копию, как реплика, и не секцию внутри одной СУБД, как партиция,
а именно отдельный сервер, ничего не знающий о соседях.

**Shard key** — поле, по которому вычисляется, на каком шарде лежит
запись. Хороший ключ обладает высокой кардинальностью и присутствует
в большинстве запросов; в этой работе им стал `user_id`.

**Router** нужен потому, что базы друг о друге не знают: кто-то должен
превратить ключ в адрес узла. В этой работе он реализован в самом
сервисе — библиотечно, без прокси.

**`hash(key) % N`** раскладывает ключи почти идеально ровно: 33.397 /
33.097 / 33.505 процента. Проблема в том, что `N` входит в формулу:
при переходе на четыре узла адрес меняется у 74.94 % ключей, причём
половина из них тасуется между старыми узлами, к новому отношения
не имея.

**Consistent Hashing** решает это, убрав `N` из вычисления адреса.
Ключ получает постоянную позицию на кольце, а узлы отвечают за участки.
Переезжает 25.62 % ключей — и, что важнее, между существующими узлами
не переезжает вообще ничего.

Плата за это — чуть худшая равномерность: 31.05 / 33.88 / 35.06 процента
кольца против почти идеальных третей у модуло. Виртуальные узлы
сглаживают перекос, но не устраняют полностью.

**Для своего сервиса я выбрал бы Consistent Hashing.** Разница
в равномерности — единицы процентов, и её добирают увеличением числа
vnode. Разница в стоимости масштабирования — это 25 % против 75 %
перевезённых данных, то есть в реальном проде разница между окном
обслуживания на час и на всю ночь. А масштабировать кластер придётся
не один раз, тогда как выиграть три процента равномерности можно
и другими способами.

Но главный урок этой работы не про выбор стратегии. Обе они одинаково
бессильны против того, что обнаружилось в задании 4: **ни один алгоритм
хеширования не спасает от перекоса, если перекос сидит в самих данных.**
Два клиента из пятидесяти тысяч держат 76 % всех заказов, и никакое
кольцо этого не исправит — такие ключи выносят на выделенный узел вручную.

## Вопросы для самопроверки

**1. Что такое shard?**
Самостоятельный экземпляр СУБД, хранящий свою непересекающуюся часть
данных. От реплики отличается тем, что хранит часть, а не копию;
от партиции — тем, что это отдельный сервер, а не секция внутри одной
базы.

**2. Что такое shard key?**
Поле, от которого вычисляется номер шарда. В этой работе — `user_id`.

**3. Почему нельзя просто случайно распределять записи?**
Потому что записать — половина дела, надо ещё уметь найти. При случайном
размещении единственный способ достать запись — опросить все узлы,
то есть каждый запрос становится распределённым, и весь смысл
шардирования теряется. Хеш-функция даёт детерминированный адрес:
по ключу всегда получается один и тот же шард.

**4. Как работает hash(key) % N?**
Ключ превращается в число, число делится с остатком на количество
шардов, остаток и есть номер узла. Просто, быстро, не требует
дополнительного состояния — роутеру достаточно знать `N`.

**5. Почему изменение количества shard'ов — проблема?**
Потому что `N` участвует в вычислении адреса каждого ключа. Меняется
`N` — меняется адрес почти у всех: измерено 74.94 % ключей при переходе
3 → 4. До завершения переноса кластер находится в состоянии, когда часть
данных лежит по старым адресам, а часть по новым.

**6. Что такое Consistent Hash Ring?**
Замкнутое кольцо значений хеш-функции, на которое кладут и узлы, и ключи.
Ключ обслуживает первый узел по часовой стрелке от его позиции. Адрес
ключа при этом не зависит от количества узлов.

**7. Почему при добавлении shard'а не приходится переносить все данные?**
Новый узел занимает свои точки на кольце и забирает у соседей справа
только те участки, которые оказались между его точкой и предыдущей.
Данные за пределами этих участков не двигаются вообще: измерено
2 393 593 перевезённых записи и **ноль** переездов между старыми узлами.

**8. Что такое virtual nodes и зачем они нужны?**
Каждый физический узел представлен на кольце не одной точкой, а
несколькими сотнями (здесь 256). Без них три случайные точки лягут
неравномерно, и один шард заберёт непропорционально большой участок.
Второе применение — учёт мощности: узлу с большим диском дают больше
виртуальных точек, и он пропорционально заберёт больше данных.

**9. Может ли Consistent Hashing гарантировать идеальное распределение?**
Нет. Даже с 256 vnode доли кольца вышли 31.05 / 33.88 / 35.06 процента —
разброс около четырёх процентных пунктов. Увеличение числа vnode
уменьшает разброс, но не обнуляет его. И никакое кольцо не спасает от
перекоса в самих данных: распределение ключей ровное, а распределение
объёма — 49 / 44 / 6 процентов.

**10. Что произойдёт, если один shard станет значительно более загружен?**
Он станет узким местом всей системы: время ответа определяется самым
медленным узлом, а в распределённых запросах — тем более. Лечится это
либо сменой ключа, либо выносом тяжёлых ключей на выделенный узел через
directory-based маршрутизацию, либо увеличением числа vnode, если
перекос в кольце, а не в данных. Подробный разбор — в лабораторной
работе №6.
