# Лабораторная работа №6. Запросы и архитектура после шардирования

Что стало с реальными запросами ChakChakShop после того, как пять
миллионов заказов разъехались по трём независимым PostgreSQL. Кластер —
из [лабораторной работы №5](../lab_new_5), ключ шардирования `user_id`.
Сырые логи прогонов — в [`raw/`](raw).

**Отчёт для защиты:** https://claude.ai/artifact/5zLPMiG11GKUfsrTPd4RKd

---

## 1. Архитектура

```
                       Backend
                          │
                       Router  (hash(user_id) % 3)
                  ┌───────┼───────┐
                  ▼       ▼       ▼
              Shard 0  Shard 1  Shard 2
              2 467 541  2 214 344  318 120 заказов
                654 MB     583 MB     200 MB
```

Три узла ничего не знают друг о друге. Всё, что выходит за пределы
одного шарда, сервис обязан склеивать сам — ни один PostgreSQL здесь
не видит результатов соседа.

Ниже разобраны пять классов запросов, и разница между ними
принципиальная: одни после шардирования не изменились вообще, другие
перестали быть SQL-запросом и превратились в алгоритм в коде.

---

## 2. Single-Shard Query

Главный запрос сервиса — список заказов клиента. `user_id` и есть ключ
шардирования, поэтому роутер сразу знает адрес.

```sql
SELECT id, total_amount, status, created_at
FROM orders
WHERE user_id = '000275af-58e2-4d65-9f02-ff7033e4051b'
ORDER BY created_at DESC
LIMIT 20;
```

```json
{ "shardsQueried": [0], "elapsedMs": 2.0, "rows": 5 }
```

```
 Limit  (actual time=0.018..9.209 rows=20 loops=1)
   Buffers: shared hit=8 read=15
   ->  Index Scan using ix_orders_user_created on orders
         Index Cond: (user_id = '000275af-...'::uuid)
 Execution Time: 9.465 ms
```

### Почему запросу не нужны другие узлы

Не потому, что там «скорее всего ничего нет», а потому, что там ничего
быть **не может**. Роутер вычисляет шард детерминированно: один и тот же
`user_id` всегда даёт один и тот же номер. Записи этого клиента физически
некуда попасть на другой узел — их туда никто не положит.

Проверено прямым перебором:

```
    shard 0: 30 заказов
    shard 1: 0 заказов
    shard 2: 0 заказов
```

Это и есть главная выгода правильно выбранного ключа: запрос после
шардирования выглядит ровно так же, как до него, и стоит столько же.
Более того — он стал дешевле, потому что индекс на узле теперь строится
по 2.4 млн строк вместо 5 млн.

## 3. Агрегирующий запрос

```sql
SELECT status, count(*) AS orders, round(sum(total_amount)) AS revenue
FROM orders GROUP BY status;
```

Здесь `user_id` в условии нет. Ключа нет — адреса нет — приходится
спрашивать всех.

Каждый узел честно отвечает за свою часть:

| | Shard 0 | Shard 1 | Shard 2 |
|---|---|---|---|
| `Cancelled` | 492 595 | 442 792 | 63 477 |
| `Completed` | 493 096 | 441 977 | 63 925 |
| `Pending` | 493 592 | 441 822 | 63 836 |
| `Processing` | 494 990 | 443 585 | 63 554 |
| `Refunded` | 493 268 | 444 168 | 63 328 |

Три частичных ответа, которые кто-то обязан сложить.

### Ответы на вопросы задания

**1. Можно ли выполнить такой запрос на одном shard?**
Нет. Любой из трёх ответов — правда лишь про свою треть данных.
Сложить их внутри SQL невозможно: узлы не видят друг друга, между ними
нет ни FDW, ни общего каталога.

**2. Где должны объединяться результаты?**
В приложении. В этой работе — в `ShardedOrderReader.ScatterGatherAsync`:

```csharp
// Узлы опрашиваются параллельно. Последовательный обход сложил бы
// задержки шардов, а так общее время равно самому медленному узлу.
var tasks = Enumerable.Range(0, ShardCount).Select(async shard => { ... });
foreach (var outcome in await Task.WhenAll(tasks)) { rows.AddRange(outcome.Rows); }
```

```json
{ "total": 5000005,
  "perShard": [ { "shard": 0, "count": 2467541 },
                { "shard": 1, "count": 2214344 },
                { "shard": 2, "count": 318120 } ],
  "shardsQueried": [0, 1, 2], "complete": true, "elapsedMs": 93.35 }
```

**3. Что происходит со временем при росте числа shard'ов?**

Здесь легко ошибиться в обе стороны. Замеренные времена отдельных узлов:

```
    shard 0: 0.38 с
    shard 1: 0.46 с
    shard 2: 0.10 с
```

Данных на узле стало втрое меньше, поэтому **каждый отдельный узел
отвечает быстрее**. Но общее время распределённого запроса — это не
сумма и не среднее, а **максимум**: ответ готов, когда ответил последний.
Добавление узлов уменьшает порцию каждого, но увеличивает шанс, что
хоть один окажется медленным — и именно он определит время ответа.

Плюс к этому растут накладные расходы: N сетевых соединений вместо
одного, N результатов, которые нужно передать и склеить. На трёх узлах
это незаметно, на сотне — становится доминирующим.

## 4. JOIN

### Локальный JOIN

```sql
SELECT o.id, p.name, oi.quantity
FROM orders o
JOIN order_items oi ON oi.order_id = o.id AND oi.user_id = o.user_id
JOIN products p     ON p.id = oi.product_id
WHERE o.user_id = '000275af-...';
```

```json
{ "shardsQueried": [0], "elapsedMs": 19.28 }
```

```
 Limit  (actual time=0.085..0.108 rows=20 loops=1)
   Buffers: shared hit=66
   ->  Nested Loop
         ->  Hash Join  (Hash Cond: o.id = oi.order_id)
               ->  Index Scan using ix_orders_user_created on orders o
```

Обычный `JOIN` внутри одного PostgreSQL, 66 страниц, 0.108 мс. Никакой
распределённости — и это результат двух решений, принятых **заранее**:

1. **`order_items` шардируется тем же ключом, что и `orders`.** Ради
   этого в таблицу добавлен `user_id`, которого нет в исходной схеме.
   Позиции заказа физически лежат на том же узле, что и сам заказ.
2. **`products` скопирован на каждый шард целиком.** Справочник
   маленький и нужен всем — его реплицируют, а не шардируют.

### Ответы на вопросы задания

**1. Что произойдёт, если связанные записи на разных shard'ах?**
Обычный `JOIN` станет невозможен. PostgreSQL на shard 0 не может
прочитать таблицу с shard 1 — для него этой таблицы не существует.

**2. Можно ли выполнить такой JOIN обычным SQL-запросом?**
Нет. Придётся разложить его в приложении: прочитать левую сторону
с одного узла, собрать ключи, сходить с ними на другой узел, соединить
результаты в памяти. Это уже не запрос, а процедура — с сетевыми
задержками на каждом шаге и без транзакционной согласованности между
ними: пока идёт второй запрос, данные первого могли измениться.

**3. Какие данные пришлось бы передавать между shard'ами?**
Всю левую сторону соединения либо список её ключей. Для выборки в 20
заказов это мелочь, для отчёта по миллиону заказов — терабайты трафика.
Именно поэтому распределённые СУБД так не любят `JOIN` больших таблиц
по не-шардовому ключу.

**4. Можно ли выбрать shard key так, чтобы JOIN был локальным?**
Именно это и сделано. И вот что было бы, выбери мы `id` заказа вместо
`user_id`:

```sql
WITH spread AS (
    SELECT o.user_id,
           count(DISTINCT shardlab.shard_by_modulo(o.id::text, 3)) AS shards_touched
    FROM orders o GROUP BY o.user_id
)
SELECT shards_touched AS shards_per_user, count(*) AS users,
       round(100.0 * count(*) / sum(count(*)) OVER (), 2) AS pct
FROM spread GROUP BY 1 ORDER BY 1;
```

```
 shards_per_user | users |  pct
-----------------+-------+-------
               2 |   251 |  0.50
               3 | 49750 | 99.50
```

**У 99.5 % клиентов заказы разъехались бы по всем трём узлам.** Запрос
«мои заказы» — самый частый в сервисе — перестал бы быть single-shard
и превратился в scatter-gather. Одно решение о ключе, принятое на этапе
проектирования, определяет стоимость главного запроса на всю жизнь
системы.

### Почему не `product_id`

```
 products_total: 7

              product_id              |  items  |   pct
--------------------------------------+---------+---------
 bbbbbbbb-bbbb-bbbb-bbbb-bbbbbbbbbbb1 | 1000001 | 49.9999
 bbbbbbbb-bbbb-bbbb-bbbb-bbbbbbbbbbb3 | 1000001 | 49.9999
 aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaa1 |       2 |  0.0001
```

Семь товаров на весь каталог, и два из них держат 99.9998 % позиций.
Такой ключ не делится даже на три узла: больше семи шардов сделать
нельзя в принципе, а нагрузка легла бы на два из них. Это ровно тот
случай низкой кардинальности, про который говорят «не может быть ключом
шардирования».

## 5. ORDER BY + LIMIT

```sql
SELECT id, created_at FROM orders ORDER BY created_at DESC LIMIT 20;
```

Каждый узел отдаёт свои самые свежие заказы:

| Shard 0 | Shard 1 | Shard 2 |
|---|---|---|
| `2026-09-12 12:47:00` | `2026-09-10 14:32:19` | `2026-09-10 14:33:41` |
| `2026-09-12 12:46:47` | `2026-09-10 14:32:13` | `2026-09-10 14:32:39` |
| `2026-09-10 14:34:03` | `2026-09-10 14:32:09` | `2026-09-10 14:27:24` |

Слияние происходит в приложении:

```csharp
// Каждый шард отдаёт свой top-N. Меньше брать нельзя: все N
// глобально свежих заказов могут оказаться на одном узле.
var merged = result.Rows.OrderByDescending(r => r.CreatedAt).Take(limit).ToList();
```

### Почему недостаточно взять первые 100 с одного shard

Потому что распределение по узлам никак не связано с сортировкой.
Ключ шардирования — `user_id`, а сортировка идёт по `created_at`; между
ними нет ни малейшей зависимости. Самый свежий заказ в системе может
принадлежать любому клиенту, то есть лежать на любом узле.

Измерено на реальном глобальном top-20:

```
  откуда пришли строки глобального top-20:
    shard 0: 12 из 20
    shard 1: 6 из 20
    shard 2: 2 из 20
```

**Взяв top-20 только с самого «богатого» узла, мы получили бы 12
правильных строк из 20 и восемь неправильных.** Причём ответ выглядел бы
совершенно нормально: двадцать заказов, отсортированных по дате.
Ошибку такого рода не видно, пока кто-нибудь не сверит цифры вручную.

Отсюда же следует неприятное свойство пагинации: чтобы отдать
`LIMIT 20 OFFSET 10000`, каждый узел обязан прислать **10 020** строк,
и приложение выбросит 30 000 из 30 060. Глубокая постраничная навигация
после шардирования дорожает пропорционально номеру страницы, умноженному
на число узлов.

```
  COUNT по всем шардам           200  опрошено [0, 1], УПАЛИ 1, ЧАСТИЧНЫЙ, total=4681885, 128 мс
  ORDER BY + LIMIT по всем       200  опрошено [0, 1], УПАЛИ 1, ЧАСТИЧНЫЙ, 6 мс
```

```json
{ "total": 4681885,
  "shardsQueried": [0, 1],
  "failedShards": ["shard2: Name or service not known"],
  "complete": false }
```

### Ответы на вопросы задания

**1. Какие данные становятся недоступны?**

| Шард | Пользователей | Заказов | Доля заказов |
|---|---|---|---|
| 0 | 16 700 | 2 467 541 | 49.35 % |
| 1 | 16 550 | 2 214 344 | 44.29 % |
| **2** | **16 754** | **318 120** | **6.36 %** |

Здесь важнее вторая колонка, а не третья. Потеряно всего 6.36 % заказов —
но вместе с ними **33.5 % клиентов**, каждый из которых видит полностью
неработающий личный кабинет. Метрика «процент потерянных строк»
обманчива: пользователю не легче от того, что его треть базы маленькая.

**2. Какие endpoint'ы перестанут работать?**

| Endpoint | Что происходит |
|---|---|
| `GET /api/orders/my` для клиента с shard 2 | **500**, данных нет нигде |
| `GET /api/orders/my` для клиентов с 0 и 1 | работает как ни в чём не бывало |
| `POST /api/orders` для клиента с shard 2 | не сможет записать |
| `GET /count`, `/newest` и любая аналитика | отвечают, но **неполно** |

**3. Продолжит ли работать остальная часть сервиса?**
Да, и это принципиальное отличие шардирования от одиночной базы. Две
трети клиентов не заметят аварии вообще. При одной базе упало бы всё
и для всех.

**4. Что должен делать backend при обращении к недоступному shard?**

Реализованное поведение различает два случая:

- **Single-shard запрос** — честная ошибка. Подставлять пустой список
  нельзя: «у вас нет заказов» и «мы не можем прочитать ваши заказы» —
  разные утверждения, и первое клиент воспримет как потерю данных.
- **Распределённый запрос** — частичный ответ с явной пометкой. Поле
  `complete: false` и список `failedShards` передаются наверх, а не
  замалчиваются.

```csharp
if (failed.Count > 0 && !_options.AllowPartialResults)
{
    throw new InvalidOperationException(
        $"Распределённый запрос неполон: недоступны шарды — {string.Join("; ", failed)}");
}
```

Флаг `AllowPartialResults` существует именно потому, что решение зависит
от смысла запроса: для дашборда частичные цифры лучше пустого экрана,
для финансового отчёта — категорически хуже, чем честная ошибка.

Отдельная деталь — таймаут на узел, короче общего таймаута запроса:

```csharp
timeout.CancelAfter(_options.ShardTimeout);   // 5 секунд на шард
```

Без него упавший узел держал бы весь распределённый запрос до общего
таймаута, и отказ одного шарда превращался бы в отказ всего сервиса.
С ним `COUNT` при мёртвом shard 2 отработал за **128 мс** — быстрее, чем
при трёх живых узлах, потому что мёртвый узел отвечает отказом мгновенно.

**5. Как повысить отказоустойчивость?**
Дать каждому шарду реплику — ровно ту, что построена в лабораторной
работе №4. Шардирование и репликация решают разные задачи и не заменяют
друг друга: шардирование делит данные, репликация их дублирует.
Боевая конфигурация — это N шардов, у каждого своя реплика, с
автоматическим failover. Дополнительно помогает circuit breaker, чтобы
не долбиться в заведомо мёртвый узел на каждом запросе.

После `docker start` кластер сошёлся сам:

```
  COUNT после восстановления  200  опрошено [0, 1, 2], полный, total=5000005, 248 мс
```

## 7. Hot Shard

Строки распределены неравномерно — это видно сразу:

```
    shard 0:    2467541 заказов, 654 MB
    shard 1:    2214344 заказов, 583 MB
    shard 2:     318120 заказов, 200 MB
```

Одна и та же агрегация на трёх узлах, третий прогон на прогретом кэше:

```
    shard 0: Time: 100.993 ms
    shard 1: Time:  88.454 ms
    shard 2: Time:  14.658 ms
```

Семикратная разница. Но самое интересное не в этом.

### Почему равное количество строк ещё не означает равномерную нагрузку

Даже если бы строки легли идеально ровно по трети, нагрузка всё равно
могла бы распределиться как угодно. Строки — это про хранение, а нагрузка —
про то, **как часто и какими запросами** к ним обращаются.

Вот два запроса одинаковой формы, к одной таблице, на одном узле:

```sql
SELECT count(*), sum(total_amount) FROM orders WHERE user_id = <клиент-гигант>;
```
```
 Finalize Aggregate  (actual time=82.641..83.963 rows=1 loops=1)
   Buffers: shared hit=1681 read=25295
   ->  Parallel Seq Scan on orders
         Filter: (user_id = 'bfb455ff-...'::uuid)
         Rows Removed by Filter: 189091
 Execution Time: 84.012 ms
```

```sql
SELECT count(*), sum(total_amount) FROM orders WHERE user_id = <обычный клиент>;
```
```
 Aggregate  (actual time=0.100..0.101 rows=1 loops=1)
   Buffers: shared hit=33
   ->  Index Scan using ix_orders_user_created on orders
 Execution Time: 0.138 ms
```

**84.012 мс против 0.138 мс — в 609 раз, на одном и том же узле.**
Планировщик даже отказался от индекса для первого клиента: его заказы
занимают 77 % таблицы, и последовательное чтение дешевле. Один ключ
из пятидесяти тысяч способен занять узел целиком.

### Возможные причины горячего шарда

| Причина | Есть ли здесь |
|---|---|
| Неудачный shard key | нет — `user_id` подходит по всем критериям |
| Неравномерное распределение данных | **да**, и это главная причина |
| Популярный клиент/tenant | **да**: два аккаунта держат 76 % всех заказов |
| Определённый тип запросов | потенциально — аналитика всегда бьёт по всем узлам |

```
      username       | shard | orders_count | pct_of_all_orders
---------------------+-------+--------------+-------------------
 loadtest_user_46594 |     0 |      1900268 |             38.01
 loadtest_user_14353 |     1 |      1900019 |             38.00
 customer            |     0 |       249760 |              5.00
```

Причина здесь не в алгоритме. Хеш распределил **ключи** идеально —
33.4 / 33.1 / 33.5 процента пользователей. Он не смог распределить
**объём**, потому что объём сидит в двух ключах, а один ключ неделим
по определению: все заказы клиента обязаны лежать вместе, иначе
рассыпается вся конструкция из части 2.

*(Эти два аккаунта — следы нагрузочного генератора из лабораторной
работы №2. Данные синтетические, но ситуация абсолютно реальная: так
выглядит любой SaaS, где один корпоративный клиент генерирует больше
трафика, чем все остальные вместе.)*

## 8. Итоговый анализ shard key

### Подходит ли `user_id` для этого сервиса

**Да, и альтернативы хуже.** Но с одной серьёзной оговоркой.

### Плюсы: какие запросы стали эффективными

| Запрос | Результат |
|---|---|
| `GET /api/orders/my` | single-shard, `Index Scan`, 23 страницы |
| `POST /api/orders` | пишет в один узел, обычная локальная транзакция |
| `JOIN orders × order_items × products` | локальный, 66 страниц, 0.108 мс |
| Всё «про одного клиента» | один узел, ноль сетевых прыжков |

Ключ попал в самый частый запрос сервиса — именно этого от него и ждут.

### Минусы: какие запросы стали распределёнными

| Запрос | Что стало |
|---|---|
| `GET /api/orders?from=&to=` | scatter-gather по всем узлам |
| `GET /api/orders/{id}` | ключа нет в условии — опрос всех узлов |
| Любая аналитика: выручка, статусы, отчёты | scatter-gather + слияние в коде |
| `ORDER BY created_at LIMIT N` | top-N с каждого узла + merge |

Отдельно стоит `GET /api/orders/{id}`: он выглядит как самый простой
запрос в сервисе, но после шардирования по `user_id` стал одним из самых
дорогих. Лечится тем же приёмом, что и в лабораторной №3: передавать
`user_id` вместе с `id` в самом URL, тогда роутер снова знает адрес.

### Проблемные операции

| Операция | Насколько тяжело | Почему |
|---|---|---|
| **Aggregation** | средне | опрос всех узлов + слияние; решается предагрегацией |
| **ORDER BY + LIMIT** | средне | top-N с каждого; глубокая пагинация деградирует линейно |
| **JOIN** | **легко в этой схеме** | co-location и реплицированные справочники сделали его локальным |
| **Migration** | **тяжело** | измерено в лабораторной №5: 25 % данных при consistent hashing, 75 % при `% N` |
| **Backup** | средне | три несогласованных дампа вместо одного; снять их в единый момент времени нечем |
| **Восстановление** | **тяжело** | восстановить один шард из трёх — значит получить кластер из данных разных моментов |
| **Балансировка** | **тяжело** | перекос сидит в двух ключах, а ключ неделим |

Самое неприятное в этом списке — не `JOIN`, которого все боятся, а
**резервное копирование и восстановление**. Потеря транзакционной
согласованности между узлами не чинится выбором ключа вообще никак.

### Оставил бы я этот ключ, проектируя заново

**Да, `user_id` остался бы.** Он единственный кандидат, который
одновременно обладает высокой кардинальностью (50 004 значения),
присутствует в главном запросе сервиса и делает `JOIN` локальным.
Альтернативы проверены и хуже: по `id` заказа 99.5 % клиентов разъехались
бы по всем узлам, по `product_id` кластер ограничен семью узлами при
двух горячих, по `created_at` вся запись идёт в один «текущий» шард.

Но три вещи я сделал бы иначе.

**Первое — маршрутизация не по модулю.** `hash % N` даёт чуть лучшую
равномерность, но привязывает адреса к размеру кластера: 75 % данных
при каждом расширении против 25 % у кольца. Consistent hashing
с самого начала.

**Второе — обработка тяжёлых ключей с первого дня.** Правильно выбранный
ключ шардирования не спасает от того, что один клиент весит как треть
базы. Лечится это не хешем, а directory-based исключениями: таблица
переопределений, в которой для отдельных `user_id` прописан выделенный
узел, а все остальные ключи идут через кольцо. Стоит это одной
проверки по кэшированному словарю перед вычислением хеша.

**Третье — `user_id` в URL всех ресурсов заказа.** `GET /api/orders/{id}`
стал распределённым не потому, что ключ плохой, а потому, что API был
спроектирован до шардирования. Форма `GET /api/users/{userId}/orders/{id}`
вернула бы его в разряд single-shard, и это решение из области дизайна
API, а не базы данных.

## Вопросы для самопроверки

**1. Чем single-shard query отличается от distributed query?**
Наличием ключа шардирования в условии. Если он есть, роутер вычисляет
адрес и работает один узел; запрос выглядит и стоит так же, как до
шардирования. Если нет — опрашиваются все узлы, а результаты склеивает
приложение.

**2. Почему JOIN между shard'ами сложнее обычного?**
Потому что обычный `JOIN` — это операция внутри одного процесса над
двумя таблицами в одной памяти. Межшардовый требует передать одну
сторону соединения по сети на другой узел либо вытащить обе в приложение.
К стоимости добавляется трафик, задержка и потеря транзакционной
согласованности: пока идёт второй запрос, данные первого могли измениться.

**3. Как выполнить COUNT(*) по всем shard'ам?**
Параллельно спросить каждый узел и сложить ответы в приложении.
Параллельно — принципиально: последовательный обход сложил бы задержки,
а так время равно самому медленному узлу. Замерено: 93 мс на трёх узлах
против 380–460 мс, если бы они отвечали по очереди.

**4. Почему ORDER BY ... LIMIT требует объединения результатов?**
Потому что порядок сортировки никак не связан с распределением по узлам.
Глобально первые N строк могут оказаться на любом узле в любой пропорции —
измерено 12 / 6 / 2 из двадцати. Каждый узел обязан прислать свои top-N,
и только после слияния получится правильный ответ.

**5. Что произойдёт при отказе одного shard?**
Его данные становятся недоступны, остальные узлы работают. Single-shard
запросы к упавшему узлу возвращают ошибку, распределённые — частичный
результат. Измерено: потеря 6.36 % заказов, но 33.5 % клиентов, у которых
личный кабинет перестал работать полностью.

**6. Что такое hot shard?**
Узел, на который приходится непропорционально много данных или запросов.
Здесь это shard 0: 654 MB против 200 MB и 101 мс против 15 мс на
одинаковой агрегации.

**7. Почему выбор shard key влияет на JOIN?**
Потому что он определяет, окажутся ли связанные записи на одном узле.
Если обе таблицы шардированы одним ключом, `JOIN` локальный; если
разными — межшардовый. В этой работе `order_items` получила `user_id`
именно ради co-location, и `JOIN` остался обычным.

**8. Какие операции особенно плохо подходят для распределённых данных?**
Те, которым по природе нужны все данные сразу: глобальные агрегации,
сортировка всего набора, глубокая пагинация, уникальность по
не-шардовому ключу, транзакции через несколько узлов и согласованный
бэкап. Общее у них одно — они требуют видеть целое, а шардирование
целого больше не существует.

**9. Что произойдёт при изменении количества shard'ов?**
Часть ключей сменит адрес. Измерено в лабораторной работе №5: 74.94 %
ключей при `hash % N` и 25.62 % при consistent hashing. До завершения
переноса часть данных лежит по старым адресам, часть по новым.

**10. Чем шардирование отличается от репликации?**
Репликация копирует одни и те же данные на несколько узлов — ради
отказоустойчивости и масштабирования чтения. Шардирование разделяет
разные данные между узлами — ради объёма и масштабирования записи.
Реплика знает всё, но не принимает запись; шард принимает запись, но
знает только свою часть. Это не альтернативы, а дополняющие механизмы:
боевая конфигурация — N шардов, у каждого своя реплика.

**11. Может ли шардирование сделать отдельный SQL-запрос быстрее?**
Может, но косвенно, и только single-shard запрос. Не потому, что
считать стало быстрее, а потому, что на узле теперь втрое меньше данных:
индекс ниже, таблица меньше, кэш попадает чаще. Замерено: агрегация на
shard 2 с 318 тыс. строк — 14.7 мс против 101 мс на shard 0 с 2.5 млн.
Распределённый же запрос почти всегда медленнее, чем тот же запрос
к одной базе: к работе добавляются сеть, ожидание самого медленного
узла и слияние в приложении.
